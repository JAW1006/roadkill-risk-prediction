# 설계 결정 기록 (Design Decisions Log)

이 문서는 로드킬 위험구간 예측 프로젝트에서 내린 설계 결정들을 **왜** 그렇게
정했는지와 함께 기록한다. 코드나 커밋 로그는 "무엇을 바꿨는지"는 보여주지만
"왜 그게 맞는 선택이라고 판단했는지"는 남기지 않으므로, 캡스톤 보고서를 쓸 때나
나중에 결정을 재검토할 때 이 문서를 근거 자료로 쓴다.

## 이 문서 사용법

- 결정 하나마다 **무엇을 / 왜 / 어떤 대안을 검토했는지 / 지금 상태**를 표로 남긴다.
- 상태는 세 가지 중 하나다:
  - ✅ **확정** — 근거가 충분하거나 사용자가 명시적으로 결정함
  - ⚠️ **잠정** — 지금은 이렇게 두지만 실제 데이터·결과를 보면 바뀔 수 있음
  - ❓ **미정** — 아직 정보가 부족해 결정을 미룬 상태 (하단 "미해결 질문" 참고)
- 새 결정을 추가하거나 상태가 바뀌면(⚠️ → ✅ 등) 해당 표를 고치고, 맨 아래
  **변경 이력**에 날짜와 함께 한 줄 남긴다.

## 1. 프로젝트 범위 결정

| 결정 | 근거 | 상태 |
|---|---|---|
| CCTV 실시간 탐지는 이번 범위 제외, 향후 확장으로만 문서화 | 3개월 캡스톤 기간 내 실시간 영상처리+엣지 배포까지 하기엔 범위가 과도함. 예측 모델이 먼저 있어야 카메라 배치 우선순위도 정할 수 있어 순서상으로도 뒤에 와야 함 | ✅ 확정 (사용자 지정) |
| 모델링 순서: RandomForest/XGBoost 베이스라인 → GNN(GCN/GraphSAGE) 고도화 | 베이스라인으로 성능 하한선과 변수 중요도를 먼저 확보한 뒤, 공간적 인접성을 반영하는 GNN이 실제로 베이스라인 대비 개선되는지 검증하는 게 방법론적으로 타당함 (그래프 구조 없이도 되는 문제에 GNN부터 쓰면 개선폭을 판단할 기준이 없음) | ✅ 확정 (사용자 지정) |
| LLM은 2단계(정책 브리핑 생성 → RAG 챗봇)로 분리 | 브리핑 생성은 이미 계산된 위험도+SHAP 근거를 요약하는 상대적으로 단순한 태스크, RAG 챗봇은 임의 질의에 대응해야 하는 더 복잡한 태스크라 난이도 순서로 나눔 | ✅ 확정 (사용자 지정) |

## 2. 데이터 파이프라인 설계

| 결정 | 근거 | 대안 검토 | 상태 |
|---|---|---|---|
| 도로를 500m 단위 구간(segment)으로 분할해 예측 단위로 삼음 (`SEGMENT_LENGTH_M`, `src/preprocessing/paths.py`) | 원본 도로 링크는 길이가 제각각이라 그대로 쓰면 구간별 "노출량(exposure)"이 달라 비교가 안 됨. 고정 길이로 자르면 구간 간 비교와 GNN 인접 그래프 구성이 쉬워짐 | 100m(더 세밀하지만 GPS 오차 대비 과도), 1km(더 안정적이지만 위험 구간을 뭉뚱그림) | ⚠️ 잠정 — 문헌값이나 실제 GPS 좌표 정밀도를 확인하지 않고 임의로 500m를 고름. 실제 로드킬 지점 데이터의 좌표 오차 범위를 보고 조정 필요 |
| 구간-일자(segment-date)를 베이스라인의 샘플 단위로 사용 (`src/models/baseline/schema.py`) | 기상 조건(강수·안개 등)이 날짜별로 바뀌므로, 날짜를 유지해야 "비 오는 날 위험도" 같은 질문에 답할 수 있음 | 구간별 누적 발생 건수를 타깃으로 하는 포아송/음이항 회귀 (날짜 차원 없이 구간 단위로만 집계) | ❓ **미정 — 아래 "미해결 질문 1" 참고. 데이터 규모를 봐야 결정 가능** |
| TAAS·에코뱅크 두 출처를 `load_roadkill_points()` 한 곳에서 통합 스키마로 병합 | 두 기관이 컬럼명·좌표계가 다름. 이후 모든 모듈이 하나의 스키마만 알면 되도록 통합 지점을 하나로 둠 | 소스별로 별도 파이프라인 유지 | ✅ 확정 (구조적으로 타당, 재검토 불필요) |
| `src/models/baseline/schema.py`의 실제 컬럼명(예: `road_grade`, `road_width_m`) | `src/preprocessing`의 각 로더 docstring에서 "만들어내겠다"고 약속한 산출 컬럼명을 그대로 가져옴 | — | ⚠️ **잠정 — 이 컬럼명들은 실제 공공데이터 스키마를 본 게 아니라 제가 역으로 설계한 것.** 예: 표준노드링크의 도로등급은 문자열("고속국도")이 아니라 코드값(101/102 등)일 가능성이 높음. 전처리 구현 시점에 실제 원본 컬럼을 확인하고 다시 맞춰야 함 |

## 3. 베이스라인 모델링 설계

| 결정 | 근거 | 대안 검토 | 상태 |
|---|---|---|---|
| 평가 지표로 PR-AUC(average precision)를 주 지표로 사용 | Saito & Rehmsmeier(2015) 이후 불균형 이진분류에서 통용되는 논지: 음성이 압도적으로 많으면 ROC-AUC는 무의미한 분류기도 높게 나와 낙관적으로 왜곡됨 | ROC-AUC 단독 사용 | ✅ 확정 (통계적 근거 확실) |
| 클래스 불균형을 오버샘플링(SMOTE) 대신 `class_weight`/`scale_pos_weight`로 처리 | 오버샘플링은 CV 폴드마다 학습 데이터로만 다시 계산해야 데이터 누수를 피할 수 있어 구현이 까다로움. 가중치 방식은 누수 위험이 구조적으로 없음 | `imbalanced-learn`의 SMOTE/ADASYN (의존성은 남겨뒀고, 나중에 재현율이 부족하면 실험해볼 수 있음) | ✅ 확정 (기본값으로), 대안은 실험 여지 있음 |
| 기본 분할 전략은 구간(`segment_id`) 단위 spatial split | 같은 구간의 다른 날짜가 학습·평가에 동시에 들어가면 공간적 정보가 새어나감(leakage). 대시보드가 실제로 하는 일(관측되지 않은/새로운 구간의 위험도 추정)과 가장 가까운 평가 시나리오 | temporal split(날짜 기준) — "미래 시점 예측력"을 보고 싶을 때 쓰도록 `--split temporal` 옵션으로 남겨둠 | ✅ 확정 (기본값), temporal은 보조 옵션으로 병행 |
| `spatial_split`을 `StratifiedGroupKFold` 기반으로 구현 (2026-09-10 수정) | 순수 `GroupShuffleSplit`은 양성이 희귀하면 평가 세트에 양성이 0개가 될 수 있고, 이 경우 ROC-AUC 계산이 깊숙한 곳에서 알 수 없는 에러로 실패함. 그룹 무결성을 유지하면서 양성 비율도 최대한 균등 배분하도록 개선, 그래도 실패하면 원인을 바로 알려주는 에러를 던지도록 방어 코드 추가 | — | ✅ 확정 (버그 수정, `tests/test_baseline_pipeline.py`로 재현·검증 완료) |
| 분류 임계값을 F1 최대화 지점으로 자동 탐색 (`evaluate.py::find_best_threshold`) | 불균형 데이터에서 기본 임계값 0.5는 거의 항상 최적이 아님 | F2-score 최대화(재현율에 더 가중), 또는 "상위 위험 구간 X%를 반드시 포함" 같은 고정 재현율 기준 | ⚠️ **잠정 — 정책 목적(위험구간에 생태통로 설치 등)이라면 놓치는 비용(재현율↓)이 오탐 비용보다 클 가능성이 높음. F1은 정밀도·재현율을 동등하게 취급하므로 실제 정책 비용 구조에 맞는지 재검토 필요** |
| SHAP은 `TreeExplainer`로 전처리(원-핫 인코딩) 이후 피처 공간에서 계산 | RandomForest/XGBoost 둘 다 지원하는 가장 표준적인 트리 모델 해석 방법 | — | ⚠️ **잠정 — 원-핫 인코딩된 범주형(`road_grade_고속국도` 등)이 개별 피처로 쪼개져 나옴. LLM 정책 브리핑에 "도로 등급이 위험 요인"이라고 자연스럽게 말하려면 원래 피처 단위로 합치는 후처리가 필요 (아직 미구현)** |
| 하이퍼파라미터 튜닝 없이 고정 기본값 사용 (`n_estimators=300` 등), 단일 train/test 분할만 평가 | "베이스라인" 단계의 목적은 GNN 대비 성능 개선폭을 잴 하한선을 빠르게 확보하는 것이지 최종 성능 최적화가 아님 | k-fold 교차검증, `GridSearchCV`/`Optuna` 튜닝 | ⚠️ 잠정 — 베이스라인 단계에서는 의도된 단순화. 실제 데이터로 성능을 볼 때 지표 변동폭(분산)이 크면 교차검증으로 전환 필요 |
| `predict_proba` 출력을 보정(calibration) 없이 그대로 "위험도"로 사용 | 아직 실데이터가 없어 보정이 실제로 필요한지 판단할 수 없음 | `CalibratedClassifierCV` (Platt/isotonic) | ❓ 미정 — 대시보드에 "72% 위험" 같은 숫자를 그대로 노출할지, 순위(랭킹)만 쓸지에 따라 필요 여부가 달라짐 |

## 4. 미해결 질문 (Open Questions)

실제 데이터가 들어오기 전까지는 결정할 수 없거나, 결정하더라도 검증이 필요한 항목.

### Q1. 구간-일자 단위 이진분류 vs. 구간 단위 카운트 회귀
- **문제**: 구간 수 × 관측 일수만큼 행이 생기는데(예: 구간 5,000개 × 3년 ≈ 550만 행),
  로드킬 발생일은 아마 수천 건 이하라 양성 비율이 0.1% 이하로 극단적으로 낮아질 수 있음.
  이 정도 규모/불균형이면 학습이 비효율적이거나 무의미해질 위험이 있음.
- **대안**: (a) 지금처럼 구간-일자 이진분류 유지 + 음성 다운샘플링, (b) 주/월 단위로
  집계해 샘플 수를 줄임, (c) 구간별 누적 발생 건수를 타깃으로 하는 포아송/음이항
  회귀로 문제 자체를 바꿈 (많은 로드킬 핫스팟 연구가 실제로 이 방식을 씀).
- **결정 시점**: 실제 데이터 수집 후 구간 수와 관측 기간이 확정되면 규모를 계산해보고 결정.

### Q2. 분류 임계값을 F1 대신 재현율 우선 기준으로 바꿀지
- **문제**: 정책 적용 맥락에서 위험구간을 놓치는 비용이 오탐 비용보다 클 가능성이 높음.
- **결정 시점**: 실제 담당자(교수/실무 인터뷰 대상)에게 "놓치는 것과 잘못 경고하는 것 중
  뭐가 더 나쁜가"를 확인한 뒤 F2-score 또는 고정 재현율 기준으로 전환할지 결정.

### Q3. 500m 구간 길이가 적절한지
- **문제**: 임의로 고른 값이며 실제 좌표 정밀도·도로 밀도를 반영하지 않음.
- **결정 시점**: 로드킬 지점 데이터의 좌표 오차 범위, 도로망 밀도를 확인한 뒤 조정.
